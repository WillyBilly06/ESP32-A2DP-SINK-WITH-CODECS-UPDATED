# Bounded over-limit L2CAP receive handling — signaling and dynamic channels

The old dbt_l2cap_receive returned NO_SPACE immediately when a peer-declared payload exceeded max_pdu_payload. Runtime treated that as a resource failure and aborted the complete host. BTstack hci.c:1268–1375 keeps reassembly overruns local. The [Core 6.1 L2CAP specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-61/out/en/host/logical-link-control-and-adaptation-protocol-specification.html), sections 4/4.1, additionally requires an MTU rejection for an oversized signaling frame, using its first request identifier; identified responses do not start rejection loops. A simple local drop would leave that obligation unresolved.

Runtime now installs an owner-only over-limit chunk policy. Reassembly drains the declared length without allocating payload storage. Existing expected/received fields distinguish discard state, so no buffer or flag is added to each partial. Replacement, generation change, timeout, clear and disconnect retire it through the normal lifecycle. Continuation overshoot and zero-length fragments retain the existing wire-rejection checks. Known-link ACL packets still complete normal controller receive-credit accounting. A bare framing caller without a policy retains explicit NO_SPACE.

The channel manager scans only four-byte command headers and skips bodies across fragment boundaries. Per-link scalar state tracks declared length, offset, partial header, first request identifier and a command count saturated at two. Header identifiers and contained lengths are checked; LE permits only one command. A completely framed oversized C-frame queues one identifier-only MTU-reject job into the existing bounded inbox. Response-only frames are discarded, malformed frames are counted, and no partial command is executed. Existing TX capacity gating keeps the mandatory reject job pending until a signaling slot is available. Real inbox/reply resource exhaustion remains explicit. The wire-rejection counter is advanced only after the policy accepts containment; an INVALID policy result remains an API/invariant error rather than inheriting wire-discard status.

For dynamic Basic channels, over-limit data updates the existing oversize record and is discarded. Unknown/closed dynamic channels keep their ignore policy. LE credit-based and ERTM channels use their existing mode-local retirement path, with disconnect signaling retried under ordinary queue backpressure. Application data callbacks never receive a truncated PDU.

This stage does not complete registered fixed-protocol handling. ATT/SMP and any other registered fixed owner still produce explicit NO_SPACE on this exceptional path until their own invalid-length/error/termination policy is connected. No truncated prefix is passed to fixed_data, and no ATT/SMP error is guessed by the L2CAP layer. This remains required work; full over-limit containment is not claimed.

The separate l2cap_reassembly.oversized_pdus UART field counts over-limit declarations. Payload MTU, 16 KiB retained RX storage, 1800×8 codec input, codecs and affinities are unchanged. Whole-image BSS grows 50212→50292 bytes (+80), text grows 1308 bytes and aggregate data grows 16 bytes (including flash constants). Three strict C11 Clang analyses and the ESP-IDF 6.1 ccache build pass. Source stability is verified. No packet-injection, simulated-peer, playback or timing campaign is run under the user hold. Automatic codec startup checks, when recorded, do not qualify this new wire path.

Existing ERTM policy already enforces receive.mps+6 <= maximum_mtu, reserving ordinary control/SDU/FCS recombination overhead. No advertised parameter was changed.
