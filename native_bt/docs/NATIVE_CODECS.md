# Native codec worker: offline candidate

## Implementation and integration boundary

`dbt_codec_worker` owns a single active descriptor and its decoder, copied
encoded queue and transient fragments. It closes the current decoder and frees
the queue before constructing another; if reconfiguration fails it attempts to
reconstruct the previous selection and reports fatal if that also fails.
The single producer of both jobs and packets must remain the host owner task;
the worker alone runs decoding and invokes PCM/stream hooks. Consumers must
copy PCM in the hook before it returns and must make stream stop drain or
discard old PCM before acknowledging it. The worker is not integrated into
the probe or a profile endpoint by these files.

`dbt_sbc_codec` adapts the existing owned SBC parser and decoder to this worker.
`dbt_aac_codec` handles the selected AAC-LC CIE, a bounded LATM version-0,
single-program/single-layer AudioMuxElement, RTP sequence/SSRC discontinuity,
and fragmented payloads with a 100 ms first-fragment deadline. On expiration,
allocation failure, or interrupted assembly, fragments for the abandoned
timestamp/SSRC are discarded through its marker. The implementation supports
44.1/48 kHz, one or two channels and 1024 sample AAC-LC frames. It rejects
other data, CRC, 960-sample mode, SBR, PCE and unsupported LATM configurations.
Successful parsing of one multiplex does not make publication of several AAC
access units atomic if a later decoder/PCM callback fails.

The AAC adapter **must** use `aacdec_guarded.c` generated by
`codecs/aac/prepare_port.py` from the exact SHA-256-pinned SDK `aacdec.c`.
It refuses other source revisions for review. This unit preserves the SDK
license notice and adds checks that decoded element channels never exceed the
selected layout and exactly match it before success. The SDK's frame info
otherwise reports configured channels, so metadata checks alone cannot detect
a malformed different-channel raw block. The adapter deliberately references
the generated guard symbol; linking it with the original unguarded unit fails.
Keep `AAC_ENABLE_SBR` disabled and `AAC_MAX_NCHANS` equal to two. The
standalone SDK Helix codec sources and their existing licensing obligations
remain in place; no BTstack component or protocol wrapper is used by this
candidate. SBC requires the three generated arithmetic-port units described in
`codecs/sbc/README.md`. Integrators must configure codec endpoints and validate
their advertised CIE subsets separately, then link these sources only in the
intended native target.

`dbt_opus_codec` independently parses the Android vendor CIE and the
PipeWire Opus 05 CIE. It accepts mono/stereo at 48 kHz, Android 10/20 ms and
Opus 05 2.5/5/10/20/40 ms configurations, with no reverse stream. Frame
duration is checked against the negotiated selection before decoding and PCM
publication; malformed packets do not invoke packet-loss concealment. Fragment
assembly uses the payload header's first/last/count fields, sequence, SSRC and
timestamp, a 100 ms deadline and a 6144-byte limit. `opus_decoder_get_size` and
`opus_decoder_init` place decoder state inside the one active worker allocation;
the PCM allocation is sized to the selected frame duration and channel count.
Link standalone SDK libopus, not its Bluedroid A2DP wrapper, for native runtime.
The shared configuration CIE field was expanded to 26 bytes for Opus 05, so
all callers must rebuild against the matching header.

## Offline evidence and memory limits

Run `python native_bt/tools/check_workspace.py`, then
`python native_bt/tools/test_native_codec_aac.py`, then check the workspace
again. The test requires FFmpeg and clang, plus Windows Visual Studio Build
Tools when run on Windows. It regenerates small fixtures and outputs only under
`native_bt/_build/native_codecs/`; the JSON receipt includes fixture and source
hashes. It independently exercises the existing SDK wrapper in a separate
library using the original SDK AAC core and compares PCM bytes with the native
transport/guarded core. The SBC reference separately exercises SDK decoder
state. The reference fixtures are test-only, not production allocations.

`python native_bt/tools/test_native_codec_opus.py` builds the standalone SDK
libopus fixed-point sources and a separate test-only legacy wrapper library.
That legacy harness supplies a small parser shim for its selected CIEs; the
wrapper itself and codec backend are the SDK sources. Fourteen Android/Opus 05
configurations, each with three real encoded frames, matched both the wrapper
and a separately initialized direct decoder, including fragmented delivery.
Every vector also passed through the shared worker. Negative tests cover CIE
selection and advertised subsets, frame duration mismatch, sequence gaps,
expiry, fragment limits and allocation failures. SBC-to-Opus and reverse
switches and rollback after failed decoder and queue allocations passed. The
Linux-only `test_native_codec_opus_asan.py` prepares the same tests with
AddressSanitizer and needs no credentials; it has not yet been run in the
recorded Windows environment.

On the recorded Windows x64 run, 42 AAC frames spanning 44.1/48 kHz and
mono/stereo matched the existing wrapper byte-for-byte both as complete and
two-fragment LATM payloads. A 56-frame 48 kHz stereo SBC fixture matched the
SDK decoder byte-for-byte. The actual shared worker emitted reference-matching
PCM for both formats, and successfully restored SBC after candidate decoder
and queue allocation failures. The tests include both channel mismatch
directions, sequence wrap, fragment expiry, loss and allocation failure. These
are finite software tests; no sanitizer, target memory measurement, I2S,
Bluetooth interoperability, RF, or continuous-playback claim follows from them.

In that run, direct AAC allocation was 25,620 bytes mono or 26,388 stereo;
direct SBC was 2,834 bytes. With a 2 x 2048-byte encoded queue, the worker
retained 6,970 bytes for SBC and 30,524 bytes for stereo AAC. Its measured
codec-switch peak was 30,524 bytes. Growing an AAC fragment from 4096 to 8192
temporarily retained both buffers and reached 38,692 bytes without a worker
queue; the corresponding bound with that queue is 42,828 bytes. These are x64
allocation requests including the worker's 8-byte allocation headers, not
ESP32 heap usage, allocator overhead, task stacks, or whole-system peak.
Fragments and all codec-owned allocations are released on close. Immutable SDK
tables remain in their source translation units rather than RAM table copies.

For the Opus run, standalone active allocations ranged from 18,160 bytes for
2.5 ms mono to 34,320 bytes for 40 ms stereo; a 20 ms stereo worker with the
same 2 x 2048-byte queue retained 34,616 bytes and switching from the tested
SBC configuration peaked at 34,616 bytes. A 10 ms stereo decoder plus simultaneous
4096- and 6144-byte fragment buffers peaked at 38,816 bytes without the queue.
These x64 measurements exclude allocator overhead and decoder stack usage.

## aptX, LHDC V5 and LDAC candidates

`dbt_aptx_codec` selects standard aptX, aptX-HD or aptX-LL CIEs for 44.1/48 kHz
stereo. Its in-place context uses the existing SDK `freeaptx.c` through the
codec-owned backend unit, and a 1024-byte PCM scratch buffer is released with
the active codec. It emits 32-bit left-aligned interleaved samples and checks
input word alignment. LL reverse audio and new-capability flags are not yet
supported. The media hook consumes an already-separated encoded payload;
whether a source uses an RTP header must be handled by the eventual transport
integration. Some malformed packet failures may follow earlier PCM publication
from that same packet. The SDK backend is LGPL-2.1-or-later; its license and
relinking obligations require review before distribution. Do not separately
compile `freeaptx.c` beside `dbt_aptx_backend.c` into the same target.

`test_native_codec_aptx.py` generated actual encoded streams with the SDK codec
and compared worker PCM byte-for-byte with a separate SDK decoder context for
all three variants at both rates. The selected configuration and the bounded
packet queue retained 9,608 bytes on the recorded Windows x64 run; switching
from the tested SBC configuration peaked at 9,608 bytes. Decoder and queue
allocation-failure rollback passed. This is codec evidence, not peer transport,
low-latency performance, or acoustic qualification.

`dbt_lhdcv5_codec` is an unadvertised candidate using the existing sibling
decoder. The sibling's entropy histories were static BSS and its reciprocal
table was a mutable RAM copy, so the generated four-unit port moves entropy
state to the active allocation, places precomputed reciprocal values in const
storage, and routes the sibling's decoder and transform allocations through
the active worker's accounting. A single-slot compile-time guard preserves the
one-worker ownership assumption. Do not link the original versions of those
four units or the earlier `dbt_lhdcv5` session adapter into the same target.
The generated source pins and hashes are in `lhdc_port/lhdc_port.json` under
the fixed build directory. The existing decoder and generated port still need
full encoded-frame validation; do not expose an LHDC endpoint on this evidence.

`test_native_codec_lhdcv5.py` checked 12 CIE configurations, invalid CIEs,
fragment expiry and allocation failure, SBC switch/rollback, and all 15
observed 192 kHz/24-bit open allocation sites. The generated reciprocal table
matched the original float division for all 161 entries. At that setting the
recorded Windows x64 worker held 61,632 bytes and its open/switch peak was
65,296 bytes; that includes generated-cache allocation requests and the
configured packet queue but excludes allocator overhead, stack and controller
memory. **No valid LHDC frame or PCM was decoded in this test.** Existing
standalone transform tests do not establish this new port's full PCM output.

`dbt_ldac_configure`, `dbt_a2dp_ldac_validate`, and `dbt_ldac_packet_parse`
are metadata-only groundwork; no LDAC worker descriptor or decoder is
registered. Synthetic tests cover 12 mono, dual and stereo configurations and
bounded, complete unfragmented frame headers. They do not validate audio frames.
The available SDK decoder accepts 44.1, 48, 88.2 and 96 kHz; its source rejects
the 176.4/192 kHz IDs even though the existing baseline advertises them. A safe
decoder adapter, fragmented LDAC support and valid encoded-frame fixtures remain
open. The SDK's LDAC parser can reconfigure itself from the frame header, so a
future adapter must verify frame format and bounds before publishing PCM.

The optional `test_native_codec_asan.py aptx|lhdcv5` runs the respective tests
under Linux AddressSanitizer without credentials. Those runs have not been
executed in this Windows session. Codec-owned component recipes exist for aptX
and LHDC but have not been target-linked here. Target linking, endpoint
integration, complete codec parity, sanitizers, licensing review and
hardware-observed decoding are still required.
