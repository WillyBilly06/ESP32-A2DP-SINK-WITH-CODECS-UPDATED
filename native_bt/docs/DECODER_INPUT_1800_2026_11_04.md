# Decoder input packet capacity: 1800 by 8

The requested experiment retains eight encoded decoder slots and increases
each payload capacity from 1008 to 1800 bytes. The advertised AVDTP media
L2CAP receive MTU also becomes 1800; increasing only decoder storage would
leave the earlier channel rejection unchanged. Controller ACL buffer sizes
and normal HCI fragmentation/reassembly remain unchanged.

Payload reserve is 14,400 bytes. With each slot's 16-byte metadata/alignment,
the packet allocation is 14,528 bytes plus its 8-byte accounting header:
14,536 total, up from 8,200. The increase is **6,336 bytes**. Queue depth and
all PCM buffers, codec configurations, core affinities and DSP modes stay
unchanged for this comparison.

Separate periodic CRC/time-protected records report L2CAP delivered SDU sizes
and last dynamic-channel oversize rejection, then decoder payload capacity,
stride, reserve, maximum seen payload and size-rejection count. Existing
queue-full, decoder rejection and PCM-backpressure records remain separate.
L2CAP last-rejection fields describe all dynamic channels and include the PSM;
they must not be assumed to represent an A2DP rejection without that identity.

The first recorded queue-full drop in the earlier trace is only 628 bytes;
its oversized-channel counter is zero. Larger packet compatibility is therefore
a defensible test, not an established explanation for that scheduling failure.

## Local verification

The actual worker passes ASan/UBSan without signed-overflow wrapping: 1001,
1008, 1009, 1799 and 1800-byte payloads are accepted, 1801 bytes is rejected,
source reuse does not alter copied first/last bytes, eight full slots reject
the ninth independently of the size counter, and FIFO ownership survives the
32-bit publication-counter wrap. Lifecycle cleanup returns all allocations.
L2CAP negotiation accepts 1800-byte RX independently of a 1024-byte peer TX
MTU; 1009/1800-byte SDUs are delivered and 1801 is rejected.

All 185 portable host groups and threaded ownership checks pass. The actual
async probe with real SBC/Opus/AAC/aptX codecs passes. The all-codec ESP-IDF6.1
image builds with ccache, source/layout admission passes, and the limited
IRAM callback audit reports no unsafe direct calls (four indirect calls remain
unproven). These are local checks, not RF continuity or maximum-LHDC proof.

The general host runner now excludes standalone executable tests with their
own main function, while retaining support units such as the no-CRT memory
helpers. Each host translation unit uses ccache separately before linking.

## Live result: capacity is not the observed drop cause

[Exact RF results](DECODER_INPUT_1800_RF_RESULTS_2026_11_04.json) bind image
017a6bba0831 and its archived ELF/source manifest. The archive was frozen before
implementation commit 48a964e7; the tested codec worker, probe, capacity header
and DSP files match that working source by hash. Android confirms LHDC V5 at
192 kHz/S24/stereo with the 1000 kbps nominal target; actual encoded bitrate is
not exposed. The ESP32 separately records CIE `00ff3a050000354c0102110000`.
All 37 pre-controller codec configurations pass on the target.

The largest delivered media SDU is **640 bytes** and the largest decoder payload
**628 bytes**. Both L2CAP oversize rejection and decoder size-rejection counters
remain zero. Queue-full drops reach 5601 and PCM backpressure 8667. These
packets already fit the former 1008-byte capacity, so the larger reserve does
not fix this workload's dropouts. This does not rule out different peers using
larger SDUs within the newly advertised limit.

Maximum-rate output allocates and briefly runs: 293568 source frames reach DMA,
with 40768 bytes recorded minimum free heap and no allocation failure. Playback
still fails: 2896832 underrun frames and one descriptor-order fault. The fault
has valid pool/shape, expected descriptor 2, observed 0, 1024-byte descriptor,
and a preceding EOF gap of **11741 us** while not stopping. The application
callback itself reaches only 45 us; this is not a measurement of all SDK/IRQ
execution. Renderer work averages 8.313 us/source frame versus the 5.208 us
rate budget, and includes preemption.

There is one core1 idle-starvation watchdog (core0 zero). Exact-ELF symbolization
places the interrupted main task in the documented controller-readiness query
called by rx-flow/runtime wait calculation. This single sample does not prove
that the query blocked or that the owner was spinning: the linked vendor query
has bounded branches and no backward loop. Task execution shares and runnable
latency remain the next measurement.

The DMA fault's ESP timer timestamp is 87452619 us and the public watchdog
hook's 87452654 us, a **35 us** separation. SDK task-WDT source prints task
diagnostics before that hook. Watchdog diagnostic activity is therefore a
plausible contributor to this EOF gap; independent interrupt-entry correlation
is still missing. Do not suppress the watchdog or relax descriptor ownership
checks to conceal the failure.

All 2302 complete periodic snapshots used here pass individual CRC/time checks;
the final truncated JSON record is excluded. The finite helper correctly fails
its runtime-health gate and observes a clean released-baseline return. The
Redmagic is confirmed paused. No feature-parity, continuous audio or maximum-rate
headroom pass is claimed.
