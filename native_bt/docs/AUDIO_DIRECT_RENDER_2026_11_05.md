# Direct processing in unpublished output-ring spans — 2026-11-05

The prior block renderer converted up to 128 stereo frames into a 1024-byte stack array, ran the integer DSP, then copied those processed samples into output pages. This was an avoidable intermediate output copy. The updated renderer converts directly into a contiguous renderer-owned free output span and runs the same DSP block API there. Each DSP call is bounded by 128 frames, the current 512-frame page edge and the logical ring edge. A short final span is processed before return.

Ownership is unchanged: the renderer snapshots output read with acquire semantics and writes at most that conservative free count. DMA can consume only the previously published written range. Neither the physical write cursor nor output.written is published until every span and the existing sound mix finish. The final release store still exposes the complete render call, not partially converted/DSP-processed samples. Input read publication remains after rendering; decoder input cannot be overwritten while conversion reads it. Close/reopen/producer-format changes still require existing quiescence/ticket fences.

No ring size, PCM precision, codec configuration, FIR bank/history/phase, DSP coefficients, interpolation, gain, fade or limiter arithmetic changes. Page/ring splits can change DSP call boundaries; the existing block contract handles arbitrary counts through 128, coefficient-ramp prefixes, one-sample identity history and bypass fade completion. The scalar compile path remains available. Direct storage is naturally aligned by the existing output-page allocation validation. Mixing remains after all DSP, with its original contiguous-span traversal. The DSP internal split-branch scratch and configured render task stack are unchanged.

The pinned BTstack reference is `port/esp32/components/btstack/btstack_audio_esp32_v5.c:230–256`: its playback callback fills a transfer buffer directly before a zero-wait driver write. Its S16/driver architecture is not our full-precision FIR/DSP/DMA architecture, and is not copied or integrated. The comparison supports reviewing staging/ownership, not claiming equivalent measured speed or replacing required quality processing.

The compiler-only profiling variant also exposed an existing C11 integration defect: esp_cpu.h includes Xtensa helpers using the GNU-only bare asm spelling. On Xtensa, the profiling code now uses the SDK XTHAL_GET_CCOUNT accessor from xtensa/core-macros.h, which reads the same per-core CCOUNT with __asm__. Other architectures retain the existing esp_cpu accessor. No undocumented controller register or altered time unit is introduced. Profile counters still include preemption and are elapsed core cycles.

Verification is source review, strict Clang analysis and target compilation only so far. The target block renderer own frame decreases from 1120 to 112 bytes under matched O3/SDK settings, a 1008-byte compiler-frame reduction; this is not full-chain stack headroom. The target object render section has no memcpy relocation after the change (the prior object had two call sites, each with literal and instruction relocations).
